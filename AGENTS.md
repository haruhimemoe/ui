# AGENTS.md

`@haruhimemoe/ui`: React components for the haruhime.moe osu! tools. Next.js 16, React 19 and Tailwind 4.1+ are peer dependencies. `tsc` compiles `src/` to `dist/` one file at a time (no bundler); `src/theme.css` ships as `dist/theme.css`. The README is the user documentation: keep it in step with the code.

## Layout

- `src/index.ts`: the public API. Export only what apps should use.
- `src/theme.css`: the palette as Tailwind colors (driven by `--hue`, `--h1-l`, `--h2-l`), the `font-sans` stack, the focus ring, and the `@source "./"` line that points an app's Tailwind at `dist/`.
- `src/components/<group>/<Name>.tsx`: one exported component per file. Groups: `basics`, `forms`, `actions`, `icons`, `filters`, `meta` (`JsonLd`: no UI, only a `<script>`), `osu` (beatmap display pieces from plain numbers, and `PlayerCard`, osu!-web's user card from a snapshot; it never fetches), `shell`, `tables` (`Table`, `THead`, `TBody`, `Th`, `Td`), `content` (since 0.11.0: a content section's nav and page grid, see below).
- `src/components/<group>/<name>Styles.ts`: class builders and class constants shared by several components (`buttonClasses`, `linkClasses`, `fieldClasses` and `FIELD_LABEL`, `tables/tableStyles.ts`, `basics/cardStyles.ts` with `CARD`, `CARD_HEADING` and the public `HeadingLevel` type).
- Internal files. `src/index.ts` exports none of their runtime code, only a few types from them, which are public API (the README documents each): `FieldProps`, `SiteLinkItem`, `RangeSliderValue` (re-exported through `RangeSlider.tsx`) and `HeadingLevel`.
  - `forms/FieldFrame.tsx`: the label, hint and error layout (`FieldFrame`, `FieldError`), the `<id>-hint` / `<id>-error` ids the fields share (`hintId`, `errorId`, `fieldDescribedBy`), `fieldControlProps` (the id, `aria-describedby` and `aria-invalid` every control gets), and the public `FieldProps` type.
  - `basics/AutoLink.tsx`: next/link or a plain `<a>`, by href, with `rel="noreferrer"` on an off-site new tab and next/link's own props dropped there. `ButtonLink`, the nav and the footer render it.
  - `filters/GroupFrame.tsx`: the labelled fieldset (`hideLabel` gives role none) that `ChipGroup`, `ChoiceChips` and `RangeSlider` share. `filters/chipStyles.ts`: the chip classes `Chip` and `ChoiceChips` share. `filters/rangeMath.ts`: RangeSlider's pure math (guarded bounds and step, normalizing, snapping, keys, drags, typed boxes). `filters/RangeBox.tsx`: one of its edit boxes, holding the draft.
  - `actions/PaginationStatus.tsx`: the client "Page X of Y" text that takes focus when a Pagination link goes away. `actions/pages.ts`: `normalizePages`, which cleans a page and page count from a URL. `actions/PaginationButton.tsx`: button mode's client Previous / Next, with finished classes (no `cx`). `actions/useLatestStatus.ts` and `actions/StatusOutput.tsx`: the latest-run-only status and its keyed `<output>`, shared by `CopyButton` and `AsyncButton`.
  - `shell/links.ts` (the public `SiteLinkItem` type, plus `canBeCurrent`, `ariaCurrentFor` and `linkItemKey`, the one React key for nav and footer entries), `shell/NavItem.tsx` (one nav entry), `shell/LinkNote.tsx` (the "soon" note beside an entry) and `shell/NavListClient.tsx` (the client list that sets `aria-current`). `shell/haruhimeTools.ts` is public (`HARUHIME_TOOLS`, `haruhimeToolsColumn`, SiteFooter's `tools`).
- `src/components/osu/playerLinks.ts`: internal, PlayerCard's pure helpers (profile and avatar URLs, osu-web's flag URL from a country code, `countryName` through `Intl.DisplayNames`, `isAnimatedImage`), tested in `tests/components/osu/playerLinks.test.ts`; the card itself in `PlayerCard.test.tsx`. PlayerCard uses plain `<img>` (with a `biome-ignore lint/performance/noImgElement` each) because next/image would make every app list osu!'s hosts in `images.remotePatterns`.
- `src/components/basics/tabIds.ts`: `tabId` and `tabPanelId`, public plain functions (server-safe) that tie a `Tabs` tab to its panel.
- `src/components/content/`: a content section's nav and page grid, section-agnostic (since 0.11.0). `types.ts`: `ContentNavItem` (`href`, `title`, optional `navTitle` and `badge`), `ContentNavGroup` (`heading?`, `items`) and `ContentSearchItem` (a `ContentNavItem` plus `description` and `keywords`, for a later `ContentSearch`), plain and server-safe, with no next-kit or brand import: a caller resolves its own entries (a docs registry today, a blog section later) into these shapes. `ContentNav.tsx` (client, a port of bb's `DocsNav`): the index link plus each group, the current page's link marked `aria-current="page"`, `navTitle ?? title` in a `line-clamp-2` span with the full `title` on the link's `title` attribute, a badge beside the label, finished class strings (no `cx`). `ContentLayout.tsx` (server, a port of bb's docs layout grid): the 14rem nav column from `lg` up beside the page, taking `nav` as an already-rendered slot so it isn't coupled to `ContentNav`.
- `src/mdx.ts`: the `@haruhimemoe/ui/mdx` subpath. Every export is a server component or a plain server-safe function; `CodeBlock` is the only async one (it awaits the highlighter). `src/remark/`: the `@haruhimemoe/ui/remark` subpath, plain functions only (no React, no `unified`/`unist-util-visit`/`@types/mdast` imports), with its own recursive walker (`mdast.ts`: `MdNode`, `walk`, `setProperty`, `textContent`) over hand-rolled mdast types. `index.ts` is `remarkHaruhime`'s default export (the module name Turbopack's `remarkPlugins` needs) plus the named `remarkCodeMeta` (`codeMeta.ts`), `remarkCallouts` (`callouts.ts`, the `[!NOTE]`/`[!TIP]`/`[!WARNING]` blockquote marker) and `remarkHeadingIds` (`headingIds.ts`); `slugify.ts` holds `slugify` and `createSlugger`, imported by both `src/mdx.ts` (re-exported) and `src/components/mdx/MdxHeading.tsx`.
- `src/components/mdx/`: the MDX element overrides and their pieces. `mdxComponents.ts` is the `{ a, blockquote, h2, h3, pre, table }` map. `MdxLink.tsx`, `MdxHeading.tsx`, `MdxPre.tsx`, `MdxTable.tsx`, `MdxBlockquote.tsx` are the overrides themselves (none exported from `src/mdx.ts` directly; `mdxComponents` is); each drops react-markdown's `node` prop. `CodeBlock.tsx`, `Callout.tsx`, `parseCodeMeta.ts` and `textOf.ts` (text content of a react-markdown children tree) are internal helpers `src/mdx.ts` re-exports individually. `CodeCopyButton.tsx` is the one client file here (`"use client"`, no `cx`, like `NavListClient`): `CodeBlock` renders it. `highlighter.ts` names Shiki only through `import type`; it stores a `HighlighterLoader` in a `globalThis` slot (`Symbol.for`) that `src/shiki.ts` fills, so `getHighlighter()` works (or warns once and returns `null`) whether or not an app registered one. `src/shiki.ts` (the `@haruhimemoe/ui/shiki` subpath) is the **only** file that loads `shiki` for real, and only through dynamic `import()` (`shiki/core`, `shiki/engine/javascript`, `shiki/langs/<name>.mjs`); everywhere else in `src/`, `shiki` appears only as `import type`, checked by `tests/packaging.test.ts`. `package.json`'s `sideEffects` lists `./dist/shiki.js` so bundlers keep a bare `import "@haruhimemoe/ui/shiki";`; the playground's `next.config.ts` adds the same rule for webpack's dev build of `src/shiki.ts` directly (Turbopack and a built `dist/shiki.js` already carry a side-effect marker; webpack resolving the un-built `.ts` file through the playground's `extensionAlias` doesn't, so it needs its own `module.rules` entry or the import gets tree-shaken and nothing highlights).
- Tests: `tests/components/mdx/` (one file per component/module: `CodeBlock.test.tsx`, `CodeCopyButton.test.tsx`, `Callout.test.tsx`, `mdxComponents.test.tsx`, `elements.test.tsx` for the link/heading/table overrides together, `highlighter.test.ts`, `parseCodeMeta.test.ts`, `textOf.test.tsx`) and `tests/remark/` (`index.test.ts`, `callouts.test.ts`, `codeMeta.test.ts`, `headingIds.test.ts`, `slugify.test.ts`).
- `src/components/palette/`: the command palette (since 0.8.0). Pure, server-safe modules first: `types.ts`, `fuzzy.ts` (the scorer: letters match at word starts or consecutively, backtracking), `calc.ts` (shunting-yard, no eval), `hotkeys.ts` (shortcut parsing and matching, no `navigator.`: `platform.ts` holds `isMac` so this stays importable from server-safe files), `recents.ts` (localStorage, silent when it throws), `store.ts` (the reducer: a stack of page frames plus the argument prompt), `rows.ts` (the row builder: recents, ranked matches, calculator, provider states, hints). Client: `paletteEvents.ts` (`openCommandPalette`, a window event), `useProviderSearch.ts` (debounce, abort, dispatch), `PaletteInput.tsx`, `PaletteList.tsx`, `CommandPalette.tsx` (the `<dialog>`), `CommandPaletteButton.tsx`, `siteCommands.ts`. `PaletteRow.tsx` and `PaletteFooter.tsx` are server-safe presentational parts with finished class strings and no `cx`. Tests: `tests/components/palette/`, one file per module and `CommandPalette.<topic>.test.tsx` per behavior, with the fixtures in `tests/helpers/palette.tsx`; `tests/setup/dom.ts` polyfills `showModal` and `close` for jsdom.
- `src/utils/`: `cx.ts` (`cx`, tailwind-merge, public since 0.4.0) and `href.ts` (`isExternalHref`, re-exported from `shell/links.ts`).
- `tests/components/<group>/`: tests in the same group as their source, `<Name>.test.tsx` for components and `<name>.test.ts` for plain modules (`forms/fieldStyles.test.ts`, `shell/links.test.ts`, which also covers `isExternalHref`, `filters/rangeMath.test.ts`). Some internal files have their own test (`basics/AutoLink.test.tsx`); the rest are covered through the components that use them. A suite that grows past about 200 lines splits by topic, `<Name>.<topic>.test.tsx` (`RangeSlider.keyboard.test.tsx`, `RangeSlider.boxes.test.tsx`), with its shared setup in `tests/helpers/` (`rangeSlider.tsx`).
- `tests/utils/cx.test.ts`, `tests/helpers/axe.ts` (`expectNoAxeViolations`), `tests/setup/dom.ts` (jest-dom matchers, cleanup).
- `tests/environment.test.tsx`: guards the test setup itself. `next/link` renders in jsdom without a router, and the axe helper catches a real violation.
- `tests/packaging.test.ts`: what ships. `.js` on next imports, `"use client"` on every file with hooks or browser APIs, no tailwind-merge in client files that server components render, the Tailwind peer range, no declaration maps, and the changelog's shape.
- `tests/theme.test.ts`: the theme's variables and the contrast values the README gives for other hues.
- `playground/`: a Next.js app that imports `../src` through a tsconfig path, for trying components by hand (`bun run play`, `bun run play:build`). It has no `package.json`: it shares the root `node_modules`, so there is one React and one lockfile. It runs with `--webpack` because `src/` imports its own files as `.js` and webpack's `extensionAlias` maps those to `.ts`/`.tsx` (Turbopack can't). `bun run typecheck` covers it; Biome lints it with import extensions off. `scripts/axe-playground.mjs` (`bun run play:axe`) builds it, opens the palette in headless Chromium and runs axe over five states at two widths, contrast on; CI runs it after the consumer check.
- `scripts/check-consumer.mjs`: the consumer check. It packs the package into a throwaway Next.js app, runs `next build`, and checks the README's claims about which navs hydrate and where tailwind-merge ships. The app's source is real files in `scripts/consumer-fixture/src/`: Biome lints them, and `bun run typecheck` checks them against `src/` through `scripts/consumer-fixture/tsconfig.json`. Render every new export there. It also builds an `/mdx` fixture page (`@next/mdx`, `remark-gfm` plus `@haruhimemoe/ui/remark` as a Turbopack module-name string) and checks three `role="note"` callouts, one `data-highlighted` line, Shiki token colors, the fence `title`, both heading ids, an unknown-language fence staying plain, and the table's `role="group"` scroll wrapper, then runs browser axe over it like `/`. Last, with no failures yet, it removes `shiki` and the fixture's `@haruhimemoe/ui/shiki` imports and rebuilds: `/mdx` must still prerender, with plain code and no `--shiki-token-` in the output, proving an app without Shiki still builds.

## Rules

- **Server-safe by default.** A component with no state, effects or browser APIs has no directive and works in Server Components. Put `"use client";` only in a file that needs it (hooks, event handlers it defines itself, `window`, `navigator`), as the first statement, right after the file header (`tests/packaging.test.ts` checks the first statement). Keep client files small. A client file can import the directive-less components (`CopyButton` renders `Button`, `ChipGroup` renders `Chip`, `NavListClient` renders `NavItem`); they become client code there. It can't import server-only code (async components, server APIs).
- **Client files that a server component renders get finished class strings.** `NavListClient`, `PaginationStatus`, `PaginationButton` and `CodeCopyButton` never import `cx`, so tailwind-merge stays on the server. `NavLinks` merges the classes and passes them down. `tests/packaging.test.ts` and the consumer check enforce this.
- **`shiki` loads only through `src/shiki.ts`, and only through dynamic `import()`.** Turbopack resolves even a dynamic `import("shiki/core")` at build time, so an app without `shiki` installed (an optional peer) fails to build if anything else imports it eagerly. Every other file in `src/` names `shiki` only as `import type` (for `HighlighterCore`, `ThemedToken`); `tests/packaging.test.ts` greps for a non-type `from "shiki` outside `src/shiki.ts` and fails the build if it finds one.
- **Next.js only.** Use `next/link` for internal links and `next/image` where it helps. No other framework shims. Import them with the `.js` suffix (`next/link.js`, `next/navigation.js`): next has no exports map, so bare specifiers break Node ESM and Vitest in consuming apps (`tests/packaging.test.ts` enforces this).
- **No site-specific copy.** Text, links, URLs and brand names come in as props. Defaults may be generic English ("Clear filters"), never a site's own wording. The one exception is the haruhime.moe family itself: the wordmark, the footer's parent and GitHub defaults, and `shell/haruhimeTools.ts` (`HARUHIME_TOOLS`, the live tools every footer links). Add a tool there when it goes live.
- **Look comes from the palette.** Use the theme's colors (`b1` to `b6`, `c1` to `c4`, `h1`, `h2`) and Tailwind's scale. No hex values, no `hsl()` in class names, no new CSS variables without adding them to `theme.css`. Exceptions: `HaruhimeWordmark` hard-codes the brand's white and pink (`fill="#ffffff"`, `fill="#ff66ab"`) so it looks the same at every `--hue`, and `StarRating` colors its pill from osu!'s star-rating spectrum (`osu/starColors.ts`, `rgb()` triplets set inline), which is osu!'s own data and also hue-independent. `PlayerCard`'s online ring is `border-lime-400`, osu!'s own green-light, for the same reason. Leave those. Ports of existing site components keep their classes exactly.
- **Native props pass through.** Props extend the element's own (`ComponentProps<"button">` and so on). `ref` is a normal prop in React 19: no `forwardRef`. Merge `className` with `cx`, caller last. Exceptions: on `DiscordIcon`, `GitHubIcon` and `HaruhimeWordmark` (and `wordmarkClassName` on `HaruhimeWordmarkLink`), the class replaces the default size instead, as the README says.
- **Accessible.** WCAG 2.2 AA. The README's "Accessibility" section lists the house rules (visible 2px focus everywhere, 24px targets, no opacity on text, live regions mounted before they speak, focus never falls to the body, few named landmarks, focusable scroll regions, native first). Every component has an axe check in its tests; interactive ones get keyboard tests. Contrast is checked by the theme test and, for the sites, a Playwright axe pass; jsdom can't compute it.
- **Exact pins.** Every dependency version is exact. Peer dependencies are ranges.
- **Relative imports end in `.js`** (`./buttonStyles.js`), even from `.tsx` files. The published files are ESM, and Next resolves them strictly. Biome enforces this.
- **Docs move with the code.** A new or changed prop, default or behavior updates the README in the same change, plus a line under `## [Unreleased]` in `CHANGELOG.md`. While on 0.x, a new API or a visual change is a minor version and a patch release holds only fixes (`tests/packaging.test.ts` checks this). Never edit a released changelog entry.
- Code style: Biome (2 spaces, double quotes, 100 columns, sorted Tailwind classes). Every file starts with the `@file / @desc / @author / @created / @modified` header. Exported functions and components get JSDoc with `@function`, `@param`, `@returns`.

## Before calling a change done

```sh
bun run check && bun run typecheck && bun run test && bun run build
bun run check:consumer   # packs the package into a throwaway Next.js app, runs next build, then axe in Chromium
bun run play:axe         # builds the playground and runs axe over the command palette's open states
```

The consumer check's axe pass (`scripts/check-consumer.mjs`, Playwright + `@axe-core/playwright`, `bunx playwright install chromium` once) runs WCAG 2.2 AA and best-practice rules with color contrast on over the fixture page at 1280 and 390 wide. It sees what jsdom can't: contrast, target size, scrollable regions, duplicate landmarks. A new component goes into `scripts/consumer-fixture/` so it gets this pass too.

CI runs `bun run test:coverage`, which fails under 90% coverage of `src/`.
